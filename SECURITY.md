# Security

## Reporting a vulnerability

Please report security problems **privately** through GitHub: **Security → Report a vulnerability** in this repository. Do not open a public issue, and do not include cookies, signed addresses or private files in a report. You will get an answer as soon as possible; fixes ship as a new release that installed copies offer as an update.

Supported version: the latest [release](https://github.com/isolmaz/SSDownload/releases/latest).

## Security model

**Local only.** The app, its command line and the browser extension talk through a per-profile named pipe that only the current Windows user can open. Clients open it at the identification level and write nothing until the process serving it is confirmed to run as the same user, so a pipe another user created under that name receives nothing. Nothing listens on the network; the media tools reach the internet only through an authenticated loopback proxy owned by the app.

**Browser bridge.** The native messaging host accepts only the fixed extension ID `hgndggnlfpnflkmnbddmcnfniamckham`, length-limited JSON (1 MiB) and an allowlist of actions: add a download, analyze media and open the picker, renew a source address, relay a browser transfer, show the window, status queries and the state of up to 100 jobs in one question, each found by the request ID the extension names: the ID it chose for its own add, or the job ID of a job added without one. The answer holds, per ID, only whether the job exists, its state, whether file bytes have arrived and its error code, never an address, name or path, and asking never starts a closed app. The browser can never choose an output path, delete files, change settings or quit the app. The extension reads a site's cookies only after you allowed that site, from one verified cookie store; a download it takes over from the browser follows the same rule, with the download's referrer as the site (no referrer, no cookies), and stays in the browser when that store cannot be verified. A download started from an allowed site's frame embedded in another page counts as that site, because its referrer is the frame's address.

**Secrets at rest.** Queue records, completion journals, site logins and the proxy password are sealed with Windows DPAPI for the current user. Cookies, headers and page markup are removed from a job once it completes. Logs and error reports strip credentials, query strings and fragments from addresses. The page markup a **Report problem** folder may hold (`sayfa.html`) is kept as is, so review it before sharing.

**Transfers.** HTTPS never downgrades on a redirect, and site headers or credentials never cross to another origin (only `Accept`, `Accept-Language` and `User-Agent` do). A file download that a redirect ends on a web page which the server does not send as an attachment (a sign-in page, for example) fails instead of saving the page, unless the file's name is a page's; the browser transfer refuses such a page the same way and never writes a web page for a video or audio job. When an address that a redirect led to expires (it answers 401, 403 or 410), the download asks the original address once more and continues on the address its redirects lead to at that moment only if that address proves the same file (an equal strong ETag, or the same Last-Modified and size, checked with `If-Range`), is not a web page and does not downgrade HTTPS; headers and credentials follow the same origin rules as the first request. It asks again only after a byte came from the fresh address, and any other outcome ends the download with the original refusal, keeping the part file. A download resumes only when the source proves it is unchanged, and only from bytes its resume record lists as flushed to disk (a record that an earlier version wrote for a one-connection download resumes from the length of the part file). Files are published atomically, never replace an existing file and are never run automatically; downloaded files carry the Windows "downloaded from the internet" mark.

**Published digests.** When you gave no SHA-256, a finished HTTP file is checked against the SHA-256 its source publishes: the `Repr-Digest` header of the response that delivered it (or of a probe request made before it) or, when neither states one and the file is at least 1 MiB, a `.sha256` or `SHA256SUMS` file next to the address you gave. The digest is published by the site that serves the file, so this detects damage in transit and a truncated body, not a malicious or compromised server, which can publish the digest of whatever it serves. When the download is redirected, the bytes may come from another server, such as a mirror, while the two small files below always come from the address you gave. A copy that is damaged or altered where it is stored, a mirror's included, is not refused when both downloads deliver the same bytes: it is kept with the note described below. Where that matters, give the SHA-256 you obtained from a separate trusted channel; it always takes precedence and nothing extra is requested. The two small files are read from the origin of the address you gave (same scheme, host and port, even when the download was redirected elsewhere) with the download's own request headers, which never go to another origin; redirects to another origin are not followed, at most two requests and 15 seconds are used for each download of the file (four requests when it is downloaded again, as below), a lookup that finds no free connection of the host in that time is skipped, and a body over 64 KiB, a web page or an unclean line is ignored. A file that does not match is deleted and downloaded once more. If the second copy has the very bytes of the first, transfer damage is ruled out and the digest is stale, describes another file, or the server's own copy is damaged, which the app cannot tell apart; the file is then kept, as it would be with no digest, and the job carries a note naming the source of the digest. If the second copy differs from the first and does not match the digest either, the download fails with `SSD-TRF-003` and the file is never published. The used re-download, with the SHA-256 of the first copy, is recorded in the job's work folder, so closing the app does not grant another.

**Processes.** Helper programs are started with argument arrays, never through a shell, inside Windows job objects owned by the app, and they run only while a job needs them.

**Media tools.** yt-dlp, Deno and FFmpeg are downloaded over HTTPS from their GitHub releases, checked against the SHA-256 published with each release, installed atomically and checked again before each use. A failed refresh keeps the working set. yt-dlp may open `file:` addresses only in the manifests the app pinned itself; a site's media description that names a `file:` address, such as a network share, is refused.

## Updates

- At most once a day the app reads `https://github.com/isolmaz/SSDownload/releases/latest/download/version.json` and its `version.json.sig`.
- The signature is Ed25519 over the exact bytes of `version.json`, verified against the public key embedded in the app (`FEED_PUBLIC_KEY` in [`src/update.rs`](src/update.rs)). The private key never enters this repository.
- The downloaded Setup must match the SHA-256 in the signed feed before it runs. Only newer `major.minor.patch` versions are offered, and nothing installs without your consent.
- The update flow never deletes files: superseded or rejected downloads move to `<profile>\update-quarantine\`.
- The browser extension is distributed through the Chrome Web Store; Chrome and Edge install and update it from there. Its ID is fixed by the `key` in `browser/chromium/manifest.json`, and the store item keeps that ID.

The Windows binaries are not Authenticode-signed yet, so SmartScreen may warn when you run a downloaded copy. Compare its SHA-256 with the value on the release page.
