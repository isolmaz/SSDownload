## Install

- **Installer:** run `SSDownload-<version>-Setup.exe`. It installs per user (no administrator rights) into `%LOCALAPPDATA%\Programs\SSDownload`, adds a Start menu entry and registers the browser connection. Optionally, it starts SSDownload with Windows.
- **Portable:** extract `SSDownload-<version>-win64.zip` to a permanent folder, run `register-native-host.cmd` once for the browser connection and open `ssdownload.exe`. Run `register-native-host.cmd` again after moving the folder.
- **Upgrading:** run the new Setup over the installed copy. It asks a running SSDownload to quit, then checks that no program still uses `ssdownload.exe` or `ssdownload-cli.exe`, such as a browser's request to the extension's native host, and waits up to 30 seconds per file for it to end. It repeats the check with the same wait right before it replaces the files, after the documents and the icon. If a program still runs, Setup shows a message, and a silent Setup (`/S`) exits with code 2. It never ends a program by force. In that case the old programs, the browser folder and the recorded version stay as they were; only the documents and the icon may already be new. Close the program and run Setup again.
- **Updates:** installed copies check the signed release feed at most once a day (**Settings → General**). A verified update is offered in a short box that names the new version and the one you run; its **What's new in <version>** link opens the release page. The update installs only after you accept it: **Install**, **Skip this version** or **Later** (Esc means Later). While a newer release waits, the main window's title shows `Update available (<version>)`, and **Help** and the tray menu offer `Install update (<version>)`. If a silent install fails (for example because a program still uses `ssdownload.exe`), the app reopens and reports Setup's exit code on its next start, such as `Setup exited with code 2`. A portable copy is not changed in place: the offer opens the release page, where you download the new ZIP.
- **Media support** (yt-dlp, FFmpeg with ffprobe, and Deno) is downloaded by the installer, which lists it as "missing components". A portable copy, an installer that could not reach the network and a silent automatic update install anything missing on the app's next start instead. Each file is checked against its published SHA-256.
  - Deno stays on major version 2: the newest stable 2.x release is taken, and a new major version is never installed by itself.
  - FFmpeg and ffprobe come from the BtbN LGPL build of the FFmpeg 9.0 release branch, not from a master snapshot. While BtbN does not publish that branch, the newest release branch it does publish is used.
  - yt-dlp comes from its newest stable GitHub release. An install or refresh that the app starts by itself (the start-up refresh, and `--setup-tools`, which the installer runs) takes the newest stable release that was published at least three days earlier. **Tools → Install media support**, the buttons of the Tools dialog and `--install-tools` / `--update-tools` take the newest one.
  - When the app starts and the installed set is a week old or older, the set is refreshed in the background, unless a video or audio download is running.
  - Before a downloaded set replaces the working one, a self-test of a few seconds runs without network access. FFmpeg generates a short clip, yt-dlp downloads it from local files with the arguments and progress lines the app uses for a download and merges it through FFmpeg, and ffprobe must read the result.
  - A set that fails the self-test is not used: the previous set stays active and the failure goes to the log. After such a failure the app starts no automatic refresh for 24 hours; a request from the menu, the dialog or the command line tries at once. When no set is installed yet, the failure is reported. A failure never blocks startup, and **Tools → Install media support** retries.
- The builds are not Authenticode-signed yet, so Windows SmartScreen may warn on first run. Compare the file with the SHA-256 on the release page before running it.

## Browser extension

The Chrome/Edge extension adds the overlay button on videos, the right-click entries and optional download takeover. It talks only to the desktop app on the same computer.

Its text (button, popup, menus and messages) is in the app's seven languages and follows the app's interface language (**Settings → General**). Until the app has reported that language (it is not installed, not running or too old), the browser's language decides when the extension has it, and English otherwise. In Arabic the popup, the welcome page and the button on the video are laid out right to left. The extension's name and summary in the store and on the browser's extensions page follow the browser's language.

- **Automatic:** Setup (and `register-native-host.cmd` for the portable ZIP) registers the [Chrome Web Store extension](https://chromewebstore.google.com/detail/hgndggnlfpnflkmnbddmcnfniamckham) with Chrome and Edge for your Windows user. The next time the browser starts, it shows a "New extension added" notice: click **Enable extension**. If the notice does not appear, close every browser window first. An extension you remove in the browser stays removed. Uninstalling SSDownload removes the registration, and the browser then removes the extension.
- **Settings → General → Install the extension in browsers** repeats the registration and opens the Chrome Web Store page, where **Add to Chrome** installs it at once. It also removes the per-user force-install policy entries for the extension that versions up to 1.6.1 wrote, because Chrome blocks the extension while one exists. If those entries need administrator rights, the app asks first (`ssdownload-cli --remove-extension-policies`).
- **Without the store:** open `chrome://extensions` (or `edge://extensions`), turn on **Developer mode**, choose **Load unpacked** and select the `browser\chromium` folder next to `ssdownload.exe` (installed copies: `%LOCALAPPDATA%\Programs\SSDownload\browser\chromium`). **Tools → Browser setup** opens that folder and the steps. The bundled copy has the same extension ID, so the browser connects it to the app the same way.
- **Toolbar popup:** the **Detection** switch (the toolbar icon reads `ON`/`OFF` in English, `AÇIK`/`KAPALI` in Turkish), **Hide the button on this site** (discovery and context entries stay), the page's media list (each entry opens the desktop picker) and **Open the app**. When the app cannot be reached, the popup says why. After a handover the icon badge counts completed downloads. Browsing alone never starts SSDownload: only an action you take (download, picker, Open the app) does.
- **Video button menu:** the arrow at the right end of the button on a video opens **Hide on this video** (**Hide on this audio** on an audio player), **Hide on this page** and **Hide on this site**. The first two last until the page is reloaded or left. The site choice is the popup's **Hide the button on this site**, where it is turned back on.
- **Extension without the app** (installed from the store first, or on macOS/Linux): it adds no video button and no context entries and takes over no downloads; browser downloads continue as usual. A fresh install that finds no app opens a welcome page once. The page says the extension needs the free Windows app and has a button to its download page. The popup then shows only **The SSDownload app is required**, the two setup steps and **Download the app**; once the app answers, the normal popup is back. SSDownload itself runs on Windows only.
- **Connection problems:** if the browser cannot connect, update the side the message names (see **Recovery**) and register the copy you use (`register-native-host.cmd` or reinstall). The app and the extension work together while they speak the same bridge protocol and capability version; their version numbers play no part.
- **A video in a frame:** the address of a player page inside another page is sometimes one the media tool cannot use (it answers `Unsupported URL`) while the page that embeds the player is. For a video in a frame, the extension therefore sends the tab's address beside the frame's (the request field `top_page_url`). It does so only when that frame is the one frame of the tab that holds a player, an embed or a sign of a player (a player container or player script in a frame where no video has a source, plays or was played). With another such frame, the page could answer with that other video, so nothing is sent.
  - When the media tool does not support the frame's address and the request names the page, the app analyses the page once and uses this analysis for the download. The picker then names the page's host (**Analyzed page**) beside the source.
  - Any other failure is shown as it is and not retried. So is the failure for a request without a top page: the page a media address or an embed was handed over from is never analysed in its place, because the tool could answer with another video of that page.
  - The field is optional, so the two sides keep working in either pairing, but the fallback needs an app and an extension newer than 1.9.0. An app of 1.9.0 or older ignores the field and analyses the frame's address. An extension of 1.9.0 or older sends none, so the app reports the media tool's error for such a frame (`SSD-MED-006`, `Unsupported URL`).

## Downloading

### Files

- **Files:** paste or drop links into **New download** (Ctrl+N), press Ctrl+V in the main window to add clipboard links, or right-click a link in the browser and choose **Download link with SSDownload**. The extension can also take over ordinary browser downloads (**Settings → Behaviour → Take over browser downloads**, off by default). It takes over only a fixed list of common file types: archives, installers and packages, disk images, documents and e-books, audio, video and `.torrent` files. Other file types, incognito downloads, blob/data downloads and extension downloads stay in the browser, and so does a download whose handover is refused.
- **Taken-over browser downloads:**
  - The browser's copy stays paused until the app's job has received file bytes or has completed, and is removed then.
  - A job that fails before its first byte (for example `SSD-NET-004`, see **Sign-in pages**) or waits for a new source address hands the download back. The browser continues it with a short notice on the active page. A job handed back while it waits for a new source address stays in the app as **Awaiting source**. If its source address is refreshed there, the file downloads a second time, so remove that job when the browser has finished the file.
  - A queued, scheduled, held or paused job keeps the browser's copy paused as long as it waits. A job you remove or cancel in the app leaves the copy paused, because you may have cancelled on purpose. A copy you resume, cancel or remove in the browser yourself is left alone.
  - The extension follows up to 100 copies at once; a 101st handover drops the oldest from the list, and that copy stays paused. It asks the app about all of them in one question, after 2 seconds, then after waits that double up to 30 seconds, and every 30 seconds through a browser alarm while its background page is suspended. While the app cannot be reached, it asks only every 30 seconds. A closed app is never started to answer.
  - A browser that is closed normally cancels its paused downloads: a copy that still waits is then gone, and the app's job simply runs on. The hand-back therefore works only while the browser stays open or after a browser crash.
  - Keeping the copy needs an app and an extension newer than 1.9.0. If either is 1.9.0 or older, the browser's copy is removed as soon as the app accepts the job.
- **New download** asks for the links (one per line), the target folder, an optional file name and the download type. **Advanced options** adds the connection count, a SHA-256 and the earliest start. An empty file name keeps the name the server gives, and an empty start time starts the download right away.
- **Detect automatically:** with this download type, a single link whose last part ends in the extension of a known file type (compared without regard to case) is added as a file at once, as an FTP link is. Every other link opens the picker: one ending in `.m3u8` or `.mpd`, one with the extension of a web page or a server script (`.html`, `.php`, `.aspx`, `.jsp`), one with an unknown extension, one with a name whose dot is part of the name (`v1.2`, `/@john.doe`, `/details/foo.bar`) and one with no extension. A job of this type (also one added with `ssdownload-cli --add`, whose `--kind` is `auto` unless given) goes to the media tools when its address ends in `.m3u8` or `.mpd` or its options need them, goes to the file download when it is an FTP address, and otherwise follows the server's answer: a web page or a playlist goes to the media tools, anything else to the file download. The known file types are:

  | Kind | Extensions |
  |---|---|
  | Archive or compressed file | `.7z`, `.bz2`, `.cab`, `.gz`, `.lz`, `.lzma`, `.rar`, `.tar`, `.tbz2`, `.tgz`, `.txz`, `.xz`, `.zip`, `.zst` (also `linux-1.0.tar.xz`) |
  | Package or installer | `.apk`, `.appx`, `.deb`, `.dmg`, `.exe`, `.img`, `.iso`, `.jar`, `.msi`, `.msix`, `.pkg`, `.rpm` |
  | Binary or data file | `.bin`, `.dat` |
  | Document | `.csv`, `.doc`, `.docx`, `.epub`, `.json`, `.md`, `.odp`, `.ods`, `.odt`, `.pdf`, `.ppt`, `.pptx`, `.rtf`, `.txt`, `.xls`, `.xlsx`, `.xml` |
  | Image | `.avif`, `.bmp`, `.gif`, `.heic`, `.ico`, `.jpeg`, `.jpg`, `.png`, `.svg`, `.tif`, `.tiff`, `.webp` |
  | Audio or video | `.3gp`, `.aac`, `.avi`, `.flac`, `.flv`, `.m4a`, `.m4v`, `.mka`, `.mkv`, `.mov`, `.mp3`, `.mp4`, `.mpeg`, `.mpg`, `.oga`, `.ogg`, `.opus`, `.ts`, `.wav`, `.webm`, `.wma`, `.wmv` |
- **File names:** a file is saved under the name you typed in **New download** or the name the browser handed over with the download. Without one, the name is the first of these that exists:
  1. The `filename` of the `Content-Disposition` header of the answer that delivers the file or, when that answer has none, of the probe request made before it.
  2. The last part of the address the file came from after the redirects, but only when the last part of the address you gave has no file extension with a letter in it and the last part of the final address ends in one. `https://host/download` redirected to `https://mirror/Setup%20159.0.exe` is saved as `Setup 159.0.exe`; `a1b2c3d4` and the `.2` of `v1.2` name nothing.
  3. The last part of the address you gave. An address that already ends in a file name (`.../report.pdf`) keeps it whatever it redirects to.

  The job list shows the last part of the address you gave (`download-` and eight characters of the job's id when the address has none) until the file is published.

  A name is cleaned the same way wherever it comes from (the sources above, **Rename** and the items of a downloaded playlist). The part up to the last `/` or `\` is dropped, except in a title the media tool read from a source, where each `/` or `\` is replaced by `_` like the characters below (`AC/DC Live` is saved as `AC_DC Live`). The characters Windows does not allow in a file name (`< > : " | ? *`), control characters and invisible format characters are replaced by `_`. The invisible ones include the bidirectional overrides that would make a name ending in `.exe` read as `exe.txt`: `<U+202E>txt.exe` is saved as `_txt.exe`. Format characters that spelling needs stay: the zero width joiner and non-joiner, the tag characters of the England, Scotland and Wales flags and the prepended concatenation marks that are drawn before the digits they belong to.
- **Segmented and resumable:**
  - A file of at least 4 MiB downloads over several connections when the server answers a one-byte range request with a matching `206 Partial Content`. The `Accept-Ranges` header is not consulted, and a missing or wrong `HEAD` length or validator neither prevents nor decides the split; only a `HEAD` that reports less than 4 MiB keeps the download on one connection. A server that ignores ranges is downloaded over one connection, and FTP downloads always use one. A connection that has no range left takes the back half of a range that another connection is still fetching, when that half is at least 2 MiB and it is expected to fetch it sooner.
  - A server that refuses `HEAD` (403, 405 or 501) or answers it with nothing is asked with a one-byte ranged `GET` in the same attempt. The `HEAD` is given 20 seconds and the `GET` 45. A failed TLS handshake or certificate check fails the attempt and is not retried (`SSD-NET-002`); the automatic retries below apply to every other failure here.
  - A download resumes only when the server proves the file is unchanged: a strong ETag, a SHA-256 you supplied, or the same `Last-Modified` and length. Otherwise it restarts instead of mixing two versions. FTP follows the same rule with the server's size and modification time; a server that does not report both, or refuses to resume, restarts the download.
  - The resume record is updated every 5 seconds or 64 MiB, whichever comes first, and when the download pauses, stops, loses its connection or finishes. After a crash or power loss, about that much is downloaded again. A resume record that cannot be read fails the attempt and keeps the partial files. The attempt is retried only when a sharing or lock violation or a transient I/O error (a timeout, an interruption, a reset, aborted or refused connection) blocked the read, never on access denied.
  - A supplied SHA-256 that does not match deletes the partial file, so a retry downloads it again. Finished files are published atomically and never overwrite an existing file: the new one is numbered before its extension (`name (1).ext`; a name that ends in `.tar` and a compression extension keeps both, as in `name (1).tar.xz`).
- **Automatic retries:** a download that fails on a network error, a timeout, a transient server answer (408, 429 and 5xx other than 501) or a file that another program holds for a moment (a sharing or lock violation) is tried again after a wait that doubles from 1 s to 60 s. A 429 or 503 that carries a `Retry-After` is waited out for that long instead, at most one hour. Network errors are an unreachable or unresolvable server or proxy, a connection cut off, reset or closed without a reply, an HTTP/2 error and a failed proxy handshake. A media tool's message counts when it names such an error or a retried `HTTP` status.
  - **Settings → Advanced** sets how many retries in a row may end without progress before the download fails (3 by default; 0 = no automatic retries).
  - An attempt that ends with more bytes kept on disk than the download had kept before (since the app started, or the download was last resumed or its source refreshed) made progress. It does not use up the limit, and the wait starts again at 1 s. A restart from the beginning, a live recording and an attempt whose kept bytes could not be measured never count as progress.
  - An attempt that stops because the download is paused, cancelled, outside its schedule window or held, or because the app closes, counts as neither progress nor a failed attempt.
  - A SHA-256 mismatch is not retried: the partial file is deleted and the download ends (**Retry failed** downloads it again).
  - After a failed attempt that made progress and met no 429 or 503, the connection count that earlier failures had halved doubles again, up to the configured number.
- **Published digests:** when you gave no SHA-256, a finished HTTP file is verified against a SHA-256 its source publishes, in this order:
  1. The `Repr-Digest` header (RFC 9530, `sha-256`) of the response that delivered the file or, when that has none, of a probe request made before it. It is compared with the bytes as stored.
  2. For a file of at least 1 MiB with no such header: `<file>.sha256` (a bare digest, or a `<digest>  <name>` or `<digest> *<name>` line naming the file) and `SHA256SUMS` (the one line naming the file) in the folder of the address you gave.

  These two files are requested only once the download is complete, with the download's request headers, and only from the origin of the address you gave, even when the download was redirected elsewhere (redirects inside that origin are followed, others never). Each download of the file uses at most two requests and 15 seconds for them. A lookup that finds no free connection of the host in that time is skipped. An answer that is not a clean `200` of at most 64 KiB, a web page, a wrong name, malformed hex or several candidate lines is ignored, and the file is published unverified. A SHA-256 you supplied is used instead, and nothing extra is requested.
  - A file that does not match a digest is deleted and downloaded once more from the beginning in the same attempt, which costs up to four lookup requests in all. The job's work folder records that second download, so closing the app does not grant another.
  - If the second copy has the very bytes of the first, transfer damage is ruled out: the digest is stale, describes another file, or the server's own copy is damaged. The file is kept, as it would be with no digest, with a note on the finished job that names the source (the log shows `transfer.digest_mismatch_consistent`).
  - If the second copy differs from the first and does not match the digest either, the download fails with `SSD-TRF-003`, is not retried and nothing is published (**Retry failed** starts over).
  - The log names the source that verified a file (`transfer.digest_verified`). The site that serves the file publishes the digest, so it detects damage in transit and truncation, not a malicious server. FTP and media (video and audio) downloads are not verified this way.
- **Batch:** a numeric or letter range such as `https://host/img[001-120].jpg` expands into up to 1000 jobs. **File → Batch download** shows an example, **Import list** loads a plain-text URL list and **Export list** writes the selected addresses.
- **Duplicates:** adding an address already in the queue asks once per batch: use the existing job, download a new copy, or cancel.

### Video and audio

- **Video and audio:** play the media and press the SSDownload button over it, use the extension's context entries, or use **File → Video download** (Ctrl+Shift+N) with the page address. Drag the button to move it off the player's own controls; it keeps that spot on every player.
  - The picker shows name, duration, thumbnail, quality (container, resolution, FPS, codec, HDR), the selected streams' total size (marked ≈ where it is estimated from the stream's bitrate) and audio and subtitle tracks. The quality list has every video quality of the source, also one whose codec the source does not name as long as it reports a resolution. A quality remembered by its height preselects only one that the chosen container can hold.
  - The name field starts from the page's title when the browser suggests it. The browser suggests only a title that names the video, not one that is just the site's name (ignoring a leading unread count such as `(3)`) or a placeholder such as `Video 1`. The app ignores a suggested name that is only the site's name or one of the extension's placeholders too. The field then starts from the title the media tool read from the source, plus the container's extension. When the player sits in a frame of another site and the tool analysed the frame, only the extension, not the app, recognises a tab title that is just the top page's site name.
  - A name you typed in **New download** is kept as typed. The name in the field when you press **Download** is the one the file is saved under.
  - A video or audio download that has no name of its own (`--add` without `--name`, **New download** with the name left empty, **Detect automatically** on a media page) is saved under the title the media tool read from the source plus the container's extension, cleaned as described under **File names**. A source without a title and a title that is only the site's name leave the name from the address; a title such as `Video 2024` is a title. A file that already has the name is never overwritten: the new one is numbered (`Title (1).mp4`). The job list shows the last part of the address until the file is published.
  - Until the analysis has loaded, the picker shows **Preparing the download...** and nothing can be downloaded yet. **Advanced options** opens the form early, for example to refresh the source of a waiting download. When the analysis fails, the picker says so, shows the reason and offers **Report problem**.
  - **Download** turns the picker into that download's window. Closing the window never cancels the download.
- **Subtitles:** subtitles the player loads itself (for example a player that draws its own captions) are offered too, once the player has loaded them, for the video and page they were loaded with. The language is read from the file name where it names one. In a subtitle file the app adds, a line that does not end after it starts is left out and lines that start at the same moment are joined into one, whatever the output format, because an MP4 file cannot store them.
- **Checks before publishing:** a missing quality or track fails instead of being silently substituted. The result is checked with ffprobe and FFmpeg before it is published:
  - Its streams are compared with your choice and the source.
  - Its duration is compared with the source's within half a second (for a source with known segment lengths, the longest segment plus 0.25 s, at least 0.25 s and at most 10 s). The check is skipped for a playlist, a live recording and a source without a duration. Audio extracted from a source that has a picture may end up to 1.5 s before the source's duration.
  - The ends of its video and audio streams are compared with each other within 1.5 s (for a source with known segment lengths, within the segment tolerance above, at most 2 s; a stream whose playlist declares its length is held to that length instead). A larger gap fails as a missing or duplicated fragment (`SSD-TRF-012`).
  - FFmpeg decodes 2 s at the start, at a third and at two thirds of the file and at its end (the middle ones only for a file longer than 6 s, the end only for one longer than 2 s), or all of the file with **Verify full content after the download finishes**. A decode error fails the job, so a download that was cut short is caught.
- **Quality limit:** a height limit (`--max-height`, or the quality the picker remembers) takes the best format whose height is known and within the limit. A format that reports no height is taken only when none with a known height fits. When no format reports a height, the best format is downloaded, and the verification afterwards fails the job with the video's height and the limit if the file is above it. A source that offers ready-made formats with audio and no separate audio track never gets a video-only format instead; for MP4, where such a format may not be remuxable, choose MKV (`SSD-MED-014`).
- **MP4 output:** the app takes the best streams that MP4 holds without re-encoding. It judges a stream by its codec and, when the source names none, by its file extension: `mp4`, `m4v`, `m4a` and `mov` fit; `ogv`, `ogg`, `oga`, `ogx`, `opus`, `webm`, `weba`, `wmv`, `wma`, `asf` and `flac` do not; a stream with any other extension is tried and checked on the output. Streams known to fit come before streams nothing is known about, whatever their size. A playlist follows the same order with one filter for every entry, except that among streams that name no codec it does not rank the `mp4`, `m4v`, `m4a` and `mov` extensions ahead of the others. When no stream fits, or a quality chosen by hand does not, the job fails at once with `SSD-MED-014` (choose MKV) and nothing is converted silently.
- **Streams with separate video and audio:** a finished, unencrypted HLS source whose video and audio come as separate playlists downloads in the app, both streams at once, each segment retried on its own.
  - A server that never answers 429 or 503 gets requests as fast as the connections allow. From its first such answer on, requests to it (both streams together) start at a steady pace a little below the rate it admitted them at, with waits that double up to 15 seconds while it admits none. Its `Retry-After` (at most 60 seconds) holds every request to it. A refused segment goes again with the next paced request after its first two refusals, then waits 1, 2, 4 and 8 seconds and then 15 seconds between attempts.
  - The status shows the speed of all streams together over the last 10 seconds and the time left of the stream that needs the longest, both once a second has been measured. After a 429 or 503 it says that the server is limiting requests. When every waiting segment is held back for 2 seconds or more, it says that it waits for the server and shows no time left.
  - The next attempt, or a download that continues after a pause, starts from the segments already stored. The streams are then copied into one file without re-encoding. If that copy fails because MPEG-TS segments end with a parameter set after their last picture, the app copies once more with repaired times and publishes that copy only after reading its times back and finding them consistent. A merge that fails ends with `SSD-TRF-002` and FFmpeg's message, with a note that the times of the video could not be restored or that the merge did not finish within its time. The job is not retried by itself.
- **Audio from HLS:** an audio download of a finished, unencrypted HLS playlist, with the audio alone or together with the video, downloads through the same downloader. FFmpeg then converts it as yt-dlp's audio extraction does, to the same file type, codec and quality, and leaves the video out. MP3, M4A, Opus and FLAC copy audio that already has that codec (AAC for M4A) and convert any other, MP3 at VBR 0 and the others at yt-dlp's default settings. **Original audio** keeps the codec (AAC as M4A) and makes MP3 at yt-dlp's default VBR 5 of a codec that has no file type of its own.
  - The status names the conversion with its share done and the time left, and the size shown stays the downloaded size until the file is saved. When a pause or the conversion's time limit (as long as the audio plays, at least 10 minutes) stops the conversion, the downloaded audio stays, and the conversion starts over when the download resumes or is retried.
  - **Original audio** of a format that already has an audio file type (such as `m4a` or `mp3`), a format of the very file type asked for, and every other source shape download through yt-dlp, which can keep such a file as it comes.
- **Picker analysis:** a download started from the picker within two minutes uses the picker's analysis instead of analyzing the page again.
- **Picker memory:** **Remember this choice for \<site\> and don't ask again** stores quality, container and audio-only per site; the next media from that site is queued directly. **MP3** queues the best audio as MP3 at the highest quality. A playlist accepts an item selection such as `1-10,15`.
- **Speed and time left of a media download:** for a download that runs through yt-dlp, the app measures the speed from the bytes that arrive, over the last 5 seconds at least. When the source sends in bursts with pauses between them (a host that answers 429 makes the downloader wait out its retries), the average spans four times the longest pause of the last minute, up to 60 seconds, so the speed and the time left stay readable between the bursts. The time left follows from that speed and the size the downloader estimates. Both update every second while the downloader prints nothing, and the speed reads 0 once no byte has arrived for a minute.
- **Size and post-processing of a media download:** the downloaded size of a job that runs through yt-dlp adds up its streams (a video, then its audio) and does not fall back when the next stream starts. While yt-dlp merges or converts the finished streams with FFmpeg, the job reads "Processing the media". That step prints nothing for as long as the local work takes, so a silent post-processor is given one hour where a silent transfer is given three minutes before the download reconnects.
- **Live streams** (live HLS and DASH channels and similar) are recorded from the moment the download starts until the stream ends. The list shows the recorded size and speed instead of a percentage. A paused live recording cannot continue the same file, so a run that resumes or retries it records new content.
- **From the stream's beginning:** for a live stream the picker offers **Download from the stream's beginning**. Where the site keeps the running stream from its start, the recording begins there and continues while the stream runs. Elsewhere the stream is recorded from the moment the download starts, and the status says so.
- **Finish live recording and keep it** (Downloads menu, or the right-click menu of a recording row) stops a running live video recording and publishes what was recorded so far as a normal file. A recording of more than 2 seconds is cut to its shortest stream and loses its last second (the frame being written when it stopped); a shorter one is published whole.
- **On sites with feeds or previews,** open the video's own page first. DRM-protected streams are not supported.

### Sign-in pages, cookies and expired links

- **Session cookies:** some downloads need the site's session. Grant **Allow session cookies for this site** in the extension for that one site. Nothing is read without that gesture, and **Remove site session permission** withdraws it. The permission covers the downloads from that site, taken-over browser downloads included, until you remove it.
  - A taken-over browser download carries cookies only when the page it came from (its referrer) is a site you allowed. A download without a referrer, such as a typed or bookmarked address, goes without cookies. A download started from an allowed site's frame embedded in another page counts as that site, because its referrer is the frame's address.
  - For an allowed site, the cookies that apply to the download address, and to the address it was redirected from when that has the same origin, are read from the browser's regular (non-incognito) cookie store. Partitioned cookies are left out, because a top-level download has no embedding page. A download whose cookie store or cookies cannot be verified (no regular tab open, several regular stores, consent recorded for another store) stays in the browser.
  - A download from a site you did not allow goes without cookies. If the site needs the session, the app reports `SSD-NET-004` (see **Sign-in pages**) and hands the download back to the browser (see **Files**), as it does for a site that answers 401 or 403 (`SSD-NET-012`; the job waits as **Awaiting source** when it has a page to refresh from). With an app or an extension of 1.9.0 or older, the browser's copy is already removed, so allow the site first.
- **Sign-in pages:** a file download fails at once with `SSD-NET-004`, without a retry, and nothing is saved, in two cases:
  - The request was redirected to a web page (`text/html` or `application/xhtml+xml`) that the server does not send as an attachment. A site sends a request that lacks the session to such a page, not the file.
  - The request reaches such a page without a redirect, the name the file is saved under ends in an extension that is not a page's, and the answer opens like a web page. The name is the one you typed or the browser handed over or, without one, the name the server suggests in `Content-Disposition`, else the last part of the address. Examples of extensions that are not a page's are `.pdf`, `.exe` and `.php`; the `.2` of `v1.2` is a version, not an extension. A server that answers for such a name with a page is sending an error or sign-in page, not the file.

  An answer opens like a web page when, after a UTF-8 byte order mark and white space, it starts with:
  - an HTML comment `<!--`;
  - the `<!DOCTYPE html>` document type;
  - one of the tags `<html>`, `<head>`, `<body>`, `<script>`, `<title>`, `<style>`, `<iframe>`, `<div>`, `<table>`, `<font>`, `<h1>`, `<a>`, `<b>`, `<br>` or `<p>`, the list of the WHATWG MIME Sniffing standard for HTML. A tag must end at white space, `/` or `>`, so `<header>` is none;
  - an XML declaration followed, after white space, comments and processing instructions such as `<?xml-stylesheet ...?>`, by an `html` document type or root element.

  The rule is relaxed from the standard's in three ways: a tag name also ends at white space other than a space and at `/`, `<!--` needs no byte after it, and a byte order mark is skipped. The XML case is an addition. A file that the server labels `text/html` by mistake, such as a `.csv`, `.txt`, `.json` or `.xml` file, does not open like a page and is saved (an XML file is a page only when it is an `html` document). The app looks at the start of its body over one connection.
  - What to do: download the file in the browser, or allow session cookies for the site from the extension's context menu and add the link again from the browser (right-click it → **Download link with SSDownload**). The extension attaches cookies only to a request it sends itself, so a retry of the failed job and a link added in the app go without them. A taken-over browser download that ends this way is continued by the browser.
  - Saved as they are: a page that the request reaches without a redirect for a name without such an extension (`download`, `v1.2`), a file whose name ends in `.htm`, `.html`, `.xhtml`, `.shtml` or `.mhtml`, and a page sent as an attachment. To save a page that an address ending in `.php` or `.pdf` answers with, name the file `.html` in **New download**.
  - An automatic job (**Auto**) whose address leads to a web page is handed to the media tools instead.
  - The experimental browser transfer applies the same rule in the browser, but takes the name from the one you typed or the browser handed over or else from the last part of the address, never from `Content-Disposition` (an answer sent as an attachment is saved all the same). It pauses the job with a message instead of writing a page that a redirect led a file job to, or that opens like a page and answers for a name with another file type's extension. It never writes a web page for a video or audio job.
- **Expired links:** many addresses redirect to a signed, time-limited address. When the address that a download was redirected to answers 401, 403 or 410, the download asks the original address and follows its redirects to a fresh address, once for each expired address.
  - Running ranges finish on their open connection. The ranges that start afterwards use the fresh address, but only if it proves the same file: an equal strong ETag, or the same Last-Modified and size, checked with `If-Range` like every resumed range.
  - A fresh address that cannot be reached, answers 401, 403 or 410 again, is another file, is a web page or is less secure (HTTP where the expired address was HTTPS) leaves the download with the original refusal and keeps what was downloaded. A refusal from the original address itself (no redirect) is not followed.
  - Asking again is not an attempt and does not use up the retry limit. An address obtained this way is renewed again only after a byte came from it.
  - When the address cannot be renewed, a job that has a page to refresh from waits as **Awaiting source** and any other job fails. **Refresh source address** (or the extension's browser transfer entry) resumes the same job with a fresh address. **Pause all** and **Start now** leave such a job waiting; **Pause all** also cancels a refresh still running for it.
  - A browser transfer that ends before it has started to receive the file (the connection to the extension closes, or the transfer is paused or cancelled) leaves the job waiting as **Awaiting source** again, and so does closing the app at that point. A transfer that ends after it started receiving pauses the job.

### Queue, windows and guards

- **Order and priority:** drag rows or use Alt+Home / Alt+End (in the Modern theme, rows can be dragged only while no column is sorted). Within a queue, queued work starts in list order, and several queues take turns. **Start now** starts a job immediately, outside the concurrency limit and outside the metered and Battery saver holds below; the free-space check still applies to it.
- **Download window:** one download you start that begins at once opens its own window: **New download** with a single link, a link or a download the browser extension hands over, and **Download** in the picker, which turns into it. Several links added together, a start scheduled for later, the site crawler, synchronization, a queue that starts a job later, **Resume all**, **Retry failed**, automatic retries, jobs restored when the app starts and `ssdownload-cli --add` open none. A download has one window; opening it again brings that window forward. Closing the window never cancels the download.
- **What the download window shows:** its title and top line name the file (the title says only Download while the name is not known yet). It names the host the file comes from and lists the status, file size, bytes downloaded with the percentage, transfer rate, time left and **Resume support**. **Resume support** is **Yes** when the next attempt keeps the bytes already downloaded (the source answers range requests and has an identity that attempt can check), **No** when it would start over, and `-` while that is not known, as for a video or audio download, an FTP download or a download not started since the app opened. A download over several connections also lists **Connections**, the parts of the file still being fetched. Under the progress bar, a second bar shows which parts of the file have arrived.
  - **Show details** shows why a waiting download waits, the error and where the file is saved, and a download that fails shows it once by itself. A download of several items lists them above the facts, which describe the selected one.
  - **Minimize** turns the window into a small card whose expand button opens it again, and **Keep on top** keeps it above other windows. No button is the default one, so Enter does nothing there.
- **Mini panel and completion card:** **Downloads → Mini panel** (or the tray) opens a small list of active downloads that can be pinned on top. A finished download shows a card with **Open** and **Show in folder**. A card never takes the focus when it appears. Click the card anywhere but on a button to use the keyboard on it: Tab and Shift+Tab move between its buttons, Enter or Space presses one and Esc closes the card. A completion card stays while the pointer is on it or one of its buttons has the keyboard focus, and goes after its time otherwise. Its buttons have names for screen readers, and it follows the colour scheme, mirrors in right-to-left languages and uses the system colours in high contrast.
- **Window position:** the main window opens where and as you left it, maximized or not. A window that starts in the tray (`--background`) takes that place when it is shown for the first time.
- **Tray:** progress on the icon; the menu has open SSDownload, the mini panel, new download, add from clipboard, batch download, pause/resume all, speed-limit presets, shut down when done, a one-hour quiet mode, the download folder, updates, Settings and Exit.
- **Disk space and sleep:** a job that is about to start is paused with a message when its disk has less than 256 MiB (or less than the remaining size) free; resume it after freeing space. Windows is kept awake while downloads run (the display may still sleep).
- **Metered connection and Battery saver:** two guards in **Settings → Behaviour**, both off by default, hold the whole queue. **Hold downloads on a metered connection** applies while Windows reports the connection as metered (a fixed or variable cost, roaming or a used-up data allowance). **Hold downloads while Windows Battery saver is on** applies while Windows has Battery saver on (Energy saver in recent Windows 11 versions); it starts at the charge level set in Windows, so the app has no threshold of its own.
  - While a guard holds, nothing starts, and running downloads (files, FTP, video and audio) go back to the queue. The status line and the Phase line in the details of a waiting download's window name the reason.
  - Once the condition ends, the queue runs again within 15 seconds, and only the downloads the hold stopped start again: a download you paused stays paused, and being held does not count as a failed attempt. **Start now** still starts a job during a hold.
  - A running live recording is not stopped by a hold, because a stopped recording cannot continue the same file. It goes on until the stream ends or you pause it. A live job that has not started yet waits like every other job; a job counts as live once the media analysis has found a live stream.
  - Windows is asked when the app starts, before any download starts, then every 15 seconds and when a guard is switched. Update checks, media-tool refreshes, synchronization checks and experimental browser transfers are not downloads of the queue and are not held.
- **Basic and Advanced** (`Basit` / `Gelişmiş`) are chosen in the first-run wizard, which also asks for the theme and, for Advanced, the usage modes (Basic switches all three on), and in Settings (**Interface level**; **Reopen the wizard** there asks again). A usage mode (Video, File or Audio) that is switched off refuses new downloads of its kind, and at least one stays on. Advanced adds named queues with time windows and byte quotas, folder rules, a site crawler, periodic synchronization, site logins, the event and job logs and completion actions (notify, shut down, run a program).
- **Completion actions:** an action runs once every job of its queue has completed. A failure in the queue, or removing one of its jobs, cancels the action until new work is added there. Shutting down and running a program also wait until every job in the list has completed (a failed, paused or cancelled job in another queue holds them back until it is retried or removed). Only one countdown runs at a time; cancelling it also cancels the other shutdown and program actions waiting behind it.
- **Byte quotas** (named queues, Advanced): a queue's byte quota counts each job's bytes once. A download that resumes, is retried or starts over by itself counts only what goes beyond the most it had downloaded. It counts the bytes a download receives, not the size of a merged or converted file.
  - A download you start over counts again from its first byte. This holds for a failed download that kept nothing on disk, whatever the cause (for example a SHA-256, supplied or published, that did not match and deleted the file, a skipped fragment that discarded the partial stream, or a failure before the first byte was stored), when you start it again; for **Refresh source address** when it starts the download over; for a browser transfer that downloads from the first byte after you restart it; and for the browser transfer of a job that **Refresh source address** (or the extension's browser transfer entry) sent to the browser, which counts every byte it fetches.
  - Each run of a live recording counts in full, since it records new content.
  - After the app is closed and opened again, a job counts on from the size it showed when it stopped. When that size was below the most it had downloaded (a download paused, failed or waiting for a new source while it had started again from fewer bytes), the bytes in between count again when they come again.

The Basic level shows only **General**, with the concurrent jobs and connections per file of **Advanced** added to it and without the usage modes, clipboard detection and daily working hours. The other tabs and those rows keep their saved values.

- **Connections per host:** the per-host limit applies to all downloads from one host together, both to how many of them run at once and to how many connections they hold open. With the default of 8, one file from a host uses up to 8 connections, and two files from the same host share those 8. A connection that cannot open because the host is at its limit waits until another one closes, and a download that waits still counts as a running download. Media downloads keep one connection of the limit free, so they fetch as many fragments at once as the media fragment concurrency allows, up to the limit minus one (4 with the defaults). A saved value of exactly 4 connections per file or 2 per host moves to 8 once, when the app first opens the profile; every other saved value stays. If version 1.9.0 or older opens and saves the profile afterwards, it drops the record of that move, and a 4 or 2 then moves again.
- **Speed limit:** **Downloads → Speed limit** sets KiB/s for the selected jobs (0 follows the global limit); the tray presets set the global limit. A running live recording keeps the limit it started with, because changing it would restart the capture.
- **Proxy:** the Windows setting is read at start and when the proxy setting is changed in Settings, and only its HTTP/HTTPS entry is used (no automatic configuration script and no SOCKS-only entry). FTP downloads go through a SOCKS5 proxy only; with an HTTP proxy they connect directly. An HTTP proxy password is sent with Basic authentication. If the proxy cannot be used at start (for example its saved password cannot be read), the app shows a warning and connects directly.
- **Site logins** (Advanced): host → user name and password, sent as HTTP Basic credentials only to that exact host over HTTPS (or HTTP when the entry allows it). Letter case, an international spelling and a trailing dot do not make a different host, and a host has one login. A redirect to another host never carries them.
- **Scheduling** uses local time; the start is inclusive, the end exclusive, `23:00–07:00` crosses midnight and equal endpoints mean all day. Manually paused work never resumes by itself.
- **Profiles:** data lives in `%LOCALAPPDATA%\SSDownload`; `--data-dir <folder>` or the `SSDOWNLOAD_HOME` environment variable selects another profile. The most recently registered copy owns the browser connection.
- **Developer mode:** `--debug` or `SSDOWNLOAD_DEBUG=1` adds **Media tools** (which, like every other text of the app, names each component by what it does and shows its version number alone) and, on the Basic level, **Diagnostics**, and skips the first-run wizard, the tour, the automatic media-tool install and refresh and the clean-up of the force-install policies that versions up to 1.6.1 wrote for the extension. The mode is saved in the profile and stays on at later starts without the option until `SSDOWNLOAD_DEBUG=0` turns it off.

## Recovery

100% transfer progress is not completion: merging and final validation still run, and only **Completed** unlocks **Open file**. Failed jobs keep their data, except a partial file whose SHA-256 (supplied, or published by the source) did not match.

| Symptom | What to do |
|---|---|
| The browser cannot connect | When the app or the extension is older than the other, the message says which one to update: the app through **Help → Check for updates**, the extension by the browser's own update or at once on its extensions page (Developer mode, **Update**). If the app showed "The browser bridge could not start" at startup, another process held its connection name: restart the app. Otherwise register the copy you use. |
| A second launch while SSDownload runs | The running copy comes to the front; no second instance starts. If that copy is still closing, the new one starts as soon as it has exited. |
| Download stays disabled after analysis | Read the error, fix the source or session, analyze again. |
| A quality or track disappeared | Analyze again and choose an available option; nothing is substituted silently. |
| Signed address expired | The download asks the original address again and goes on with the fresh address it redirects to. When that is not possible, a job that has a page to refresh from waits for **Refresh source address** instead of failing; any other job fails. |
| `SSD-NET-004`: the source answered with a sign-in or web page | The file needs your session. Download it in the browser, or allow session cookies for the site from the extension's context menu and add the link again from the browser (**Download link with SSDownload**). |
| An HLS/DASH retry says the compatibility evidence for the existing segments is missing or corrupt | The job folder holds segments of an earlier attempt and no usable record of the source they came from, so they cannot be told from another source's: remove the job and add it again. If the app stopped before it wrote the record of the request, the message says it could not tell which download the temporary files belong to: choose a new file name. A folder that holds none of a stream's files is no such case: the retry starts fresh and the earlier error stays the reason. |
| `SSD-NET-001`, `SSD-NET-003`, `SSD-NET-007`, `SSD-NET-008`, `SSD-NET-011`: no address found for the name, a proxy that could not be used, a timeout, a closed or reset connection, a server that could not be reached | The connection is at fault, not the file. The download retries by itself (see **Automatic retries**). When the retries are used up, check the network, the proxy and the address, then use **Retry failed**. |
| `SSD-NET-002`: the secure (TLS) connection could not be established: the handshake or the certificate check failed | Not retried: the secure connection is not accepted. The message gives the reason in the interface language: an authority this computer does not trust, an expired or not yet valid certificate, a certificate for another address, a revoked certificate, or another refusal. The same reasons are given when the media components, an update or a site scan cannot be fetched over a secure connection. Windows' own wording of it is in the job log and the event log. Check that the address is the right `https` one, the system clock, and any program that inspects secure connections. |
| `SSD-NET-006`: the server is busy (429, 503) | Retried by itself, after the server's `Retry-After` when it sends one (at most one hour). When the retries are used up, use **Retry failed** later. |
| `SSD-NET-013`, `SSD-NET-015`: the server failed (another 5xx except 501) or gave up waiting for the request (408) | Retried by itself after a wait that doubles from 1 s to 60 s; a `Retry-After` on these answers is not read. When the retries are used up, use **Retry failed** later. |
| `SSD-NET-005`, `SSD-NET-012`, `SSD-NET-014`: the server answered 404, 401 or 403, or another 4xx | Not retried. The address expired, moved or needs your session: add the link again from its page (see **Expired links** and **Session cookies**). |
| `SSD-NET-016`: the server does not support the request (501) | Not retried: the server does not implement the request, so the same address fails again. Try another source or mirror. |
| `SSD-MED-017`: the media tool could not finish the download | The text after the code names the stage that failed and gives the tool's output from its last `ERROR:` line on (at most its last 2 KiB); its whole output is in the job log. When that output names a status a retry can clear (408, 429, a 5xx other than 501) or a connection failure (a timeout, a reset, an empty reply, a refused or aborted connection, a failed name lookup, a proxy tunnel), the job is retried by itself (see **Automatic retries**). When the retries are used up, use **Retry failed** later. A 403 is `SSD-MED-007` instead: a job that has a page to refresh from waits for **Refresh source address** (see **Expired links**). |
| `SSD-TRF-002`: merging the streams fails, or a work folder remains | Free space and resume; parts stay under `<destination>\.ssdownload-work\jobs\<job-id>`. |
| The app stopped while a download was finishing | A finished file waits in its work folder until it is moved to the destination. When the job next starts, it moves that file there and completes without downloading again. The folder of a finished playlist is not recognised and downloads again. A file that sits beside the folder of the experimental browser transfer, or beside an archive of an earlier run of it, is not moved either: that transfer verifies its file itself. |
| `SSD-TOL-005`: the media tools' path is too long | Windows starts a program only from a path of at most 259 characters, and yt-dlp starts FFmpeg, FFprobe and Deno itself from paths that begin with `\\?\` (the prefix counts). From a longer path it carries on without them and can leave streams unmerged or in the wrong container, so the analysis and every download that runs yt-dlp are refused up front. Only a job that resumes from the source it already pinned and downloads it with the app's own HLS downloader runs no yt-dlp and is not refused. The tools sit about 120 characters below the profile folder (`<profile>\tools\versions\<id>\…`). Move the profile folder to a shorter path and start SSDownload with `--data-dir <that folder>` or `SSDOWNLOAD_HOME`; a `--data-dir` that names another folder opens a separate, empty profile. A long download folder is not affected. |
| Media verification: the file's content does not match its extension | The file holds another container than its name says (for example MPEG-TS under `.mp4`), so it is not published. Download it again; if it repeats, the source delivers that container every time: pick another container in the picker, or report the log. A single file relayed by the experimental browser transfer is copied into the job's container before it is checked. |
| Remove hits a sharing violation | Close the program holding the file and retry. |
| The queue cannot be saved | Active jobs pause and new work waits while saving is retried. |
| Encrypted records do not open | Records are bound to the Windows user (DPAPI). Unreadable ones move to quarantine and return when the profile is opened under the original account again. |
| Database from a newer version | An older build refuses a newer database instead of rewriting it. |

## Error codes and logs

- Classified failures carry permanent `SSD-<area>-<number>` codes with a message in every interface language. Areas: `BRG` browser bridge, `MED` media resolution, `NET` network, `TRF` transfer, `STO` storage, `RCV` recovery, `TOL` media tools, `UPD` updates, `EXT` extension. Codes are never renumbered or reused. The **Error** line of the details pane starts with the code and its short message and goes on with what to do next; a failure without a code gives only what to do next. The whole text of the failure is in **Error details** (the row's menu).
- A download that fails on the network carries one of these codes at the start of its error text, which **Error details** (the row's menu), the job log and **Report problem** show:
  - `SSD-NET-001`: the name has no address (DNS).
  - `SSD-NET-011`: the server could not be reached (refused, no route).
  - `SSD-NET-007`: a timeout.
  - `SSD-NET-008`: the connection was closed or reset.
  - `SSD-NET-003`: the proxy could not be found or refused the tunnel.
  - `SSD-NET-002`: the TLS handshake or the certificate check failed.
  - For an HTTP answer: `SSD-NET-005` (404), `SSD-NET-012` (401, 403), `SSD-NET-006` (429, 503), `SSD-NET-015` (408), `SSD-NET-016` (501), `SSD-NET-013` (any other 5xx) and `SSD-NET-014` (any other 4xx).

  The text after the code gives the cause, and the log marks an answer from the server with the owner `site`. Any other kind of failure, and the text errors of yt-dlp, carry no network code.
- A failed media analysis or download shows the media tool's output from its last `ERROR:` line on (from its last exception line when the tool crashed without one; at most the last 2 KiB of it) behind a code, without the Python traceback and the app's own stage notes. The tool's whole output is in the log. The codes are decided from that same output (an earlier item of a playlist, a warning or a retry that failed another way decides nothing), in this order:
  1. `SSD-MED-003`: DRM protection (analysis only; the first line of that output says so).
  2. `SSD-MED-007`: the origin answered 403 (anywhere in that output).
  3. `SSD-MED-008`: region, removal, privacy or sign-in (the first line of that output says so).
  4. `SSD-MED-006`: any other failed analysis.
  5. `SSD-MED-017`: any other failed download.

  An analysis and a download that end in the same output get the same refusal code, and an output that answers 403 and also reads as a refusal is `SSD-MED-007`. The text of a failed download names the stage that failed.
- Logs live in `<profile>\logs\`: `events-YYYYMMDD.jsonl` and `ssdownload-YYYYMMDD.log`, rotating at 5 MB with five kept and removed after 30 days, plus per-job timelines in `logs\jobs\`. The words the app writes into a log line itself (`state=`, `phase=`, `file=`, `bytes=` and the like) are English in every interface language; the text of an error stays in the language the app showed it in. A job's timeline has one `job.stage` line for every change of its state or phase (downloading media, processing, retrying, completing), and none for a count or a percentage that moves inside a phase. The browser connection appends its refusals to the same files (channel `native-host`) and leaves rotation to the app; it writes nothing when it cannot read the profile settings.
- URLs are logged without credentials, query or fragment. With **Log site names** off, site names are hidden as well, also in error messages that repeat the download's site or name a host after `host:`, `host=` or `connect to`.
- **Report problem** (on a failed analysis or job) and **Tools → Diagnostics** write a local folder and ZIP. Nothing is uploaded; look through it before sharing it in an issue. A **Report problem** folder can include the failing page's markup as `sayfa.html`, unredacted: the copy the browser handed over or, without one, the page read once by the app (address without query or fragment, no cookies, credentials or referer). It is stored as inert escaped text in a script-free document, not as executable HTML.

`ssdownload-cli.exe` (next to `ssdownload.exe`) forwards commands to the running app and prints JSON for scripts. `ssdownload-cli --help` lists everything:

|---|---|

## Data and uninstall

- Uninstalling removes the program, its shortcuts and browser registration, and **keeps your downloads and your profile**.
- Deleting `%LOCALAPPDATA%\SSDownload` removes the queue, settings, logs and media tools. A `.ssdownload-work` folder in a download folder holds the work files of unfinished jobs and is gone once none is left. A hidden `<file name>.ssdownload.claim` marker beside a download's destination reserves that name from the moment the job is added until it completes or is removed; a failed job keeps its marker and its work files for **Retry failed** until you remove it.
- See [PRIVACY.md](../PRIVACY.md) for what is stored and where.
