## Install

- **Installer:** run `SSDownload-<version>-Setup.exe`. It installs per user (no administrator rights) into `%LOCALAPPDATA%\Programs\SSDownload`, adds a Start menu entry and registers the browser connection. Optionally it starts SSDownload with Windows.
- **Portable:** extract `SSDownload-<version>-win64.zip` to a permanent folder, run `register-native-host.cmd` once for the browser connection and open `ssdownload.exe`. Moving the folder later requires running `register-native-host.cmd` again.
- **Before upgrading,** exit through the tray menu. Installed copies update themselves: SSDownload checks the signed release feed at most once a day (Settings → General) and installs a verified update after you accept it (**Install**, **Later** or **Skip this version**; Esc means Later). If a silent install fails, the app reopens and reports why on its next start. A portable copy is not changed in place: the offer opens the release page so you can download the new ZIP.
- **Media support** (yt-dlp, FFmpeg/ffprobe and Deno) is downloaded by the installer (shown there as "missing components"); a portable copy, an installer that could not reach the network, or an automatic update (silent) installs anything missing on the app's next start instead. Deno stays on major version 2: the newest stable 2.x release is taken, and a new major version is never installed by itself. FFmpeg and ffprobe come from the BtbN LGPL build of the FFmpeg 9.0 release branch, not from a master snapshot; while BtbN does not publish that branch, the newest release branch it does publish is used. yt-dlp comes from its newest stable GitHub release. Each file is checked against its published SHA-256. When the app starts and the installed set is a week old or older, it is refreshed in the background unless a video or audio download is running. An install or refresh the app starts by itself (that start-up refresh, and `--setup-tools`, which the installer runs) takes the newest stable yt-dlp release that was published at least three days earlier; **Tools → Install media support**, the buttons of the Tools dialog and `--install-tools` / `--update-tools` take the newest one. Before a downloaded set replaces the working one, it runs a self-test of a few seconds without network access: FFmpeg generates a short clip, yt-dlp downloads it from local files with the arguments and progress lines the app uses for a download and merges it through FFmpeg, and ffprobe must read the result. A set that fails the self-test is not used, the previous set stays active and the failure goes to the log; after such a failure the app starts no automatic refresh for 24 hours, while a request from the menu, the dialog or the command line tries at once. When no set is installed yet, the failure is reported. A failure never blocks startup; **Tools → Install media support** retries.
- The builds are not Authenticode-signed yet, so Windows SmartScreen may warn on first run. Compare the file with the SHA-256 on the release page before running it.

## Browser extension

The Chrome/Edge extension adds the overlay button on videos, the right-click entries and optional download takeover. It talks only to the desktop app on the same computer. Its own text (button, popup, menus and messages) is in the app's languages and follows the app's interface language (**Settings → General**); until the app has reported it (not installed, not running, an older version), the browser's language decides when the extension has it, English otherwise. In Arabic the popup, the welcome page and the button on the video are laid out right to left. The extension's name and summary in the store and on the browser's extensions page follow the browser's language.

- **Automatic:** Setup (and `register-native-host.cmd` for the portable ZIP) registers the [Chrome Web Store extension](https://chromewebstore.google.com/detail/hgndggnlfpnflkmnbddmcnfniamckham) with Chrome and Edge for your Windows user. The next time the browser starts it shows a "New extension added" notice: click **Enable extension**. Close every browser window first if the notice does not appear. If you remove the extension in the browser, it stays removed. Uninstalling SSDownload removes the registration, and the browser then removes the extension.
- **Settings → General → Install the extension in browsers** repeats the registration and opens the Chrome Web Store page, where **Add to Chrome** installs it at once. It also removes the force-install policy entries that versions up to 1.6.1 wrote, because Chrome blocks the extension while one exists. If those entries need administrator rights, the app asks first (`ssdownload-cli --remove-extension-policies`).
- **Without the store:** open `chrome://extensions` (or `edge://extensions`), turn on **Developer mode**, choose **Load unpacked** and select the `browser\chromium` folder next to `ssdownload.exe` (installed copies: `%LOCALAPPDATA%\Programs\SSDownload\browser\chromium`). **Tools → Browser setup** opens that folder and the steps. The bundled copy has the same extension ID, so the browser connects it to the app the same way.
- **Toolbar popup:** the discovery switch (`ON`/`OFF` in English, `AÇIK`/`KAPALI` in Turkish), **Hide the button on this site** (discovery and context entries stay), the page's media list (each entry opens the desktop picker) and **Open the app**. When the app cannot be reached, the popup says why. After a handover the icon badge counts completed downloads. Browsing alone never starts SSDownload: only an action you take (download, picker, Open the app) does.
- **Video button menu:** the arrow at the right end of the button on a video opens **Hide on this video**, **Hide on this page** and **Hide on this site**. The first two last until the page is reloaded or left; the site choice is the popup's **Hide the button on this site**, where it is turned back on.
- **Extension without the app** (installed from the store first, or on macOS/Linux): it adds no video button, no context entries and takes over no downloads; browser downloads continue as usual. A fresh install that finds no app opens a welcome page once, saying the extension needs the free Windows app, with a button to its download page. The popup then shows only **The SSDownload app is required**, the two setup steps and **Download the app**; once the app answers, the normal popup is back. SSDownload itself runs on Windows only.
- If the browser cannot connect, update the side the message names (see **Recovery**) and register the copy you use (`register-native-host.cmd` or reinstall). The app and the extension work together while they speak the same bridge protocol and capability version; their version numbers play no part.

## Downloading

- **Files:** paste or drop links into **New download** (Ctrl+N), press Ctrl+V in the main window to add clipboard links, right-click a link in the browser → **Download link with SSDownload**, or let the extension take over ordinary browser downloads of a fixed list of common file types: archives, installers and packages, disk images, documents and e-books, audio, video and `.torrent` files (**Settings → Behaviour → Take over browser downloads**, off by default; other file types, incognito, blob/data and extension downloads stay in the browser and a refused handover resumes there). The browser's copy stays paused until the app's job has received file bytes or completed, and is removed from the browser then; a job that fails after its first byte has already removed it. A job that fails before its first byte (for example `SSD-NET-004`, see **Sign-in pages**) or waits for a new source address hands the download back, and the browser continues it with a short notice on the active page. A job handed back while it waits for a new source address stays in the app as **Awaiting source**: if its source address is refreshed there, the file downloads a second time, so remove that job in the app when the browser finishes the file. A queued, scheduled, held or paused job keeps the browser's copy paused for as long as it waits, with no time limit. A job you remove or cancel in the app leaves the browser's copy paused, because you may have cancelled on purpose; a copy you resume, cancel or remove in the browser yourself is left alone. The extension follows up to 100 browser copies at once (a 101st handover drops the oldest from the list, and that copy stays paused in the browser) and asks the app about all of them in one question after 2 seconds, then after waits that double up to 30 seconds, and every 30 seconds through a browser alarm while its background page is suspended; a closed app is never started to answer, and while it cannot be reached the question is repeated only every 30 seconds. The extension remembers the copies while its background page restarts, but a browser that is closed normally cancels its paused downloads: a copy that still waits then is gone and the app's job simply runs on, so the hand-back works only while the browser stays open or after a browser crash, which leaves the copies paused. Keeping the copy needs an app and an extension newer than 1.9.0; if either is older, the browser's copy is removed as soon as the app accepts the job.
- **New download** asks for the links (one per line), the target folder, an optional file name and the download type; **Advanced options** adds the connection count, a SHA-256 and the earliest start. An empty file name keeps the name the server gives, and an empty start time starts the download right away.
- **Segmented and resumable:** large files (at least 4 MiB) download over several connections when the server answers a one-byte range request with a matching `206 Partial Content`; the `Accept-Ranges` header is not consulted, and the answer to `HEAD` is only a hint (a missing or wrong `HEAD` length or validator neither prevents nor decides it, and a `HEAD` that reports less than 4 MiB keeps the download on one connection). A server that ignores ranges is downloaded over one connection. The file is handed out in ranges of just under 10 MiB at most, one range to a connection at a time. A connection that has finished a range and finds none left takes the back half of a running range: half of what a slow or stalled connection still has to fetch goes to the connection that has finished, and the other half stays with the one that was running (a stalled connection goes on waiting for it, up to the 45 second low-speed timeout). The half is taken only from a range that has been flowing for a quarter of a second since its first byte (a rate seen over less than that says too little about the rate it keeps), only when it is at least 2 MiB (a range with less than 4 MiB to come stays with its connection) and only when the connection is expected to have the half before the running connection would have all the rest: the time its request for its last range of at least 2 MiB took to get the first byte, counted from when the request was sent (a shorter range can arrive in one burst, which says nothing about the rate a connection keeps up), plus the half at the rate that range arrived at from its first byte, has to be less than the rest at the rate the running range has arrived at since its first byte. A connection that has been idle for 0.2 s has closed its socket and has to open a connection for the half, so the time it waits counts as at least the time the first byte took to come for the latest range that opened a connection. Of the ranges that qualify, the one with the most bytes still to come is cut, and of the idle connections the one with the highest rate takes the part. A connection that has not finished a range of at least 2 MiB yet, or that would need longer than the running connection, leaves the running range alone, so a server that is slow to send the first byte of a range does not make the connections cut each other's ranges. The connection that was running keeps the bytes it has received and the front half of the rest. Its request still names the old end, so it receives and drops what is in flight beyond the new end, and it stops when data beyond the new end arrives or, when the server sends nothing more, within about a second of having all the bytes up to that end; either completes that range instead of failing it and frees the connection. The part taken is requested like every other range, with the recorded validator in `If-Range`, and is tried again as often as the range it was taken from; an answer for another size or validator restarts the download instead of mixing two versions. FTP downloads use one connection and are never split. A download that starts from nothing takes its size and validators from the response that delivers the bytes; a length that response states is exact, and a body that only the closing connection ends has to reach the `HEAD` length. Retained bytes stay bound to the size and validators recorded with them: a resume sends the recorded validator in `If-Range` and continues only when the server answers `206` for that size with an equal strong ETag (or an equal `Last-Modified` while no ETag disagrees), or, when that answer carries no validator, when this attempt's `HEAD` or a SHA-256 you supplied vouches for the recorded file. If `HEAD` reports another ETag than the recorded one, only the recorded strong ETag on the answer itself proves the file, except that a SHA-256 you supplied still vouches unless `HEAD`'s ETag is a strong one that conflicts with the recorded strong ETag. In every other case the download restarts. A download resumes only when the server proves the file did not change (strong ETag, a SHA-256 you supplied, or the same `Last-Modified` and length); otherwise it restarts instead of mixing two versions. FTP follows the same rule with the server's size and modification time; a server that does not report both, or refuses to resume, restarts the download. While a download runs, the received data is flushed to disk and the resume record updated once 5 seconds have passed or 64 MiB are waiting, whichever comes first (with one connection this is checked when data arrives), and when a download pauses, stops, loses its connection or finishes (not after a disk write error, nor when a source is discarded because it rejected a range, ignored ranges or changed). The flush runs beside the transfer, so the connections keep receiving, and every file handle that wrote data is flushed before the record is written. While a download runs, a flush or record update that fails keeps the previous record and is tried again after the next interval; at a pause or stop the download still pauses or stops, and later resumes from the previous record. A failed flush at the end or after a lost connection fails the attempt. A record that cannot be written at the end does not fail the download: a download over several connections goes on with the previous record in place after waiting up to about 3 s for the record (an update that is still running can spend about 1.5 s on it before the update at the end spends as much), and with one connection no record is written at the end. Publishing the file deletes the record, unless a program still holds it, and then it stays next to the file. After a lost connection the previous record stays. After a crash or power loss, about the data received since the last update is downloaded again. A resume record lists only bytes that were flushed: the ranges for several connections, including the beginning of a range still being fetched (a range that drops continues where it stopped, and the part of a range that another connection took lists nothing until that connection has flushed bytes of it), and the flushed length of the part file for one connection (a longer part file is cut back to it on resume). A record written by an earlier version, which has no such length for one connection, resumes from the length of the part file. A resume record that exists but cannot be read (for example while a virus scanner holds it) fails the attempt, keeps the partial files and is retried. A supplied SHA-256 that does not match deletes the partial file, so a retry downloads it again. Finished files are published atomically and never overwrite an existing file (`name (1).ext`).
- **Automatic retries:** a download that fails on a network error, a timeout or a transient server answer (408, 429 and 5xx other than 501) is tried again after a wait that doubles from 1 s to 60 s (or the server's `Retry-After`, at most one hour). **Settings → Advanced** sets how many retries in a row may end without progress before the download fails (0 = no automatic retries). An attempt made progress when it ends with more bytes kept on disk than this download has kept since the app started or the download was last resumed or its source refreshed: the bytes the resume record lists (the recorded ranges while several connections download; for one connection the recorded flushed length of the part file, or the length of the part file when an earlier version wrote the record), and for media the tool's partial and finished files in the work folder. Such an attempt does not use up the limit and the wait starts again at 1 s. An attempt that had to restart from the beginning because the source's identity could not be proven, a live recording and an attempt whose kept bytes could not be measured never count as progress. An attempt that stops because the download is paused, cancelled, outside its schedule window or held, or because the app closes counts as neither progress nor a failed attempt. A SHA-256 mismatch is not retried: the partial file is deleted and the download ends (**Retry failed** downloads it again). After a failed attempt that made progress and met no 429 or 503, the connection count that earlier failures had halved doubles again, up to the configured number.
- **Published digests:** when you gave no SHA-256, a finished HTTP file is verified against a SHA-256 its source publishes, in this order: the `Repr-Digest` header (RFC 9530, its `sha-256` member) of the response that delivered the file or, when that has none, of the answer to a probe request made before it; the header describes the whole file for whole and ranged answers alike and is compared with the bytes as stored (the app asks for no content coding and decodes none); then, for a file of at least 1 MiB for which no such header was found, `<file>.sha256` (a bare digest, or a `<digest>  <name>` or `<digest> *<name>` line naming the file) and `SHA256SUMS` (the one line naming the file) in the folder of the address you gave. These two files are requested only once the download is complete, only from the origin of that address even when the download was redirected elsewhere (redirects inside that origin are followed, other origins never), with the download's request headers, in at most two requests and 15 seconds for each download of the file (a lookup that finds no free connection of the host in that time is skipped, and the file is published unverified); an answer that is not a clean `200` of at most 64 KiB, a web page, a wrong name, malformed hex or several candidate lines is ignored and the file is published unverified. A SHA-256 you supplied is used instead and nothing extra is requested. A file that does not match a digest is deleted and downloaded once more from the beginning in the same attempt, outside the automatic retries above; the use of that second download, with the SHA-256 of the first copy, is recorded in the job's work folder, so closing the app does not grant another; the record stays until the file is published, the download fails with `SSD-TRF-003` or the job is removed, so a download that fails for another reason in between has no third copy. The digest files are read again for the second copy, so a file that did not match costs up to four lookup requests. If the second copy has the very bytes of the first, transfer damage is ruled out: the digest is stale, describes another file, or the server's copy is damaged, and the file is kept as it would be with no digest, with a note on the finished job that names the source (the log shows `transfer.digest_mismatch_consistent`). If the second copy differs from the first and does not match the digest either, the download fails with `SSD-TRF-003`, is not retried and nothing is published (**Retry failed** starts over). The log names the source that verified a file (`transfer.digest_verified`). The digest is published by the site that serves the file, so it detects damage in transit and truncation, not a malicious server, and a copy damaged where it is stored (a mirror's included) that both downloads deliver identically is kept with the note above. FTP and media (video and audio) downloads are not verified this way.
- **Video and audio:** play the media and press the SSDownload button over it, use the extension's context entries, or use **File → Video download** (Ctrl+Shift+N) with the page address. Drag the button to move it off the player's own controls; it keeps that spot on every player. The picker shows name, duration, thumbnail, quality (container, resolution, FPS, codec, HDR), the selected streams' total size (marked ≈ where it is estimated from the stream's bitrate) and audio/subtitle tracks. Subtitles the player loads itself (for example a player that draws its own captions) are offered too, once the player has loaded them, for the video and page they were loaded with; the language is read from the file name where it names one. In a subtitle file the app adds, a line that does not end after it starts is left out and lines that start at the same moment are joined into one, whatever the output format, because an MP4 file cannot store them; line times are read the way FFmpeg reads them (the digits after the comma are milliseconds, so `00:00:03,61` is 3.061 s). **Download** turns the picker into that download's status view; closing it never cancels the download. A missing quality or track fails instead of being silently substituted, and the result is checked with ffprobe/FFmpeg before it is published: its streams are compared with the choice and the source, its duration with the source's within a tolerance (half a second, more for a source whose HLS segments are longer; not for a playlist, a live recording or a source without a duration), and FFmpeg decodes 2 s at the start, at a third and at two thirds of the file and at its end (the middle ones only for a file longer than 6 s, the end only for one longer than 2 s; all of the file with **Verify full content after the download finishes**). A download that is cut short ends inside a frame that cannot be decoded, and so does a source whose last segment ends inside an audio frame but plays. Decoding stops half a second before the end of an audio or video stream (of one longer than a second), so that last frame is not judged, only where the source confirms that stream: a length the source gives for that kind of stream has a fractional part (the lengths its HLS playlists declare for video and for audio or, where it declares none, its duration; a length in whole seconds confirms nothing, because an extractor or an old playlist may have rounded it down by up to a second, and the tolerance the source has for segment lengths does not make it exact), the job is no playlist or live recording, and the stream itself ends at most half a second before the longest such length of its kind (a kind can list the lengths of several playlists, and a stream cut short is not confirmed by a shorter one). Every other stream is decoded to its end and fails on a cut frame; so does a file whose audio ends more than half a second before its video inside a cut frame, even when the source's tolerance accepts the lengths, because that cannot be told apart from a truncated audio download, unless the audio's own playlist declares that shorter length. A decode error before that point fails the job.
- **Streams with separate video and audio:** a finished, unencrypted HLS source whose video and audio come as separate playlists downloads both at once in the app, each at the same rate through its playlist and each segment retried on its own. A connection stays open from one segment to the next of the same server while its worker goes straight on to another segment there, or waits only for that server's pace (see below), and no other request waits for a connection to that server, or for any connection while all the connections the app allows are in use; a request refused without waiting, such as a browser transfer's, counts as waiting for two seconds. Otherwise the connection closes after its segment, so a kept connection never holds a place of the per-host limit that another request waits for, and another download from that server gets a place as the segments in progress end. A server that never answers "too many requests" (429) or "unavailable" (503) gets requests as fast as these connections allow. From its first such answer on, the requests to it, of both streams together, start at a steady pace a little below the rate it admitted them at: each burst of such answers slows the pace once, each admitted request speeds it up a little while the pace holds requests back, and while the server admits none at all the wait before the next request doubles each time, up to 15 seconds, and its `Retry-After` (at most 60 seconds) holds every request to it. A segment the server refuses goes again with the next paced request after its first two refusals, and after each later one waits before its next attempt as after other failures, 1, 2, 4 and 8 seconds and then 15 seconds, counting its failures without those two refusals, however the server answers the other segments. A refused segment also waits for its own `Retry-After`. The status shows the speed of all streams together over the last 10 seconds, and the time left of the stream that needs the longest at its own speed, rounded up to whole seconds, both once a second has been measured; a stream's speed is measured afresh from its first bytes, and again from the bytes after 10 seconds in which none came. No time left is shown while a stream that is not done has no size yet, no speed or a speed of 0, or has reached its estimated size; the size is estimated from the segments that have come. Only the bodies of 200 answers count as downloaded, and within an attempt the downloaded size does not fall when a segment fails part-way, so a queue's byte quota does not count those bytes again when they come again. After a 429 or 503 the status says that the server is limiting requests until 10 seconds after the last such answer, or 10 seconds after the pace last held back a segment that a free connection could have started, whichever is later. Once no request is in flight and every waiting segment is held back for 2 seconds or more, by its own wait (after a failure, or its `Retry-After`) or by the wait for its server after the server refused every request (the doubling wait, or its `Retry-After` then), the status says that it waits for the server and shows no time left, until a request starts again. The gaps between the requests of a steady pace are not a wait for the server, however long. A paused download continues after the segments it already has. The streams are then copied into one file without re-encoding.
- **Audio from HLS:** an audio download of a finished, unencrypted HLS playlist, with the audio alone or together with the video, downloads through the same downloader. FFmpeg then converts it as yt-dlp's audio extraction does, to the same file type, codec and quality, and leaves the video out: MP3, M4A, Opus and FLAC copy audio that already has that codec (AAC for M4A) and convert any other, MP3 at VBR 0 and the others at yt-dlp's default settings; **Original audio** keeps the codec (AAC as M4A) and makes MP3 at yt-dlp's default VBR 5 of a codec that has no file type of its own. The status names the conversion with its share done and the time left; the size shown stays the downloaded size until the file is saved, and a queue's byte quota counts the downloaded bytes, not the size of the converted file. When a pause or the conversion's time limit (as long as the audio plays, at least 10 minutes) stops the conversion, the downloaded audio stays, and the conversion starts over when the download resumes or is retried. **Original audio** of a format that already has an audio file type (such as `m4a` or `mp3`), and a format of the very file type asked for, download through yt-dlp, which can keep such a file as it comes; so does every other source shape.
- **Picker analysis:** a download started from the picker within two minutes uses the picker's analysis instead of analyzing the page again.
- **Picker memory:** **Remember this choice for \<site\>** stores quality, container and audio-only per site; the next media from that site is queued directly. **MP3** queues the best audio as MP3 at the highest quality; a playlist accepts an item selection such as `1-10,15`.
- **Speed and time left of a media download:** for a download that runs through yt-dlp, the app measures the speed from the bytes that arrive, over the last 5 seconds at least; when the source sends in bursts with pauses between them (a host that answers 429 makes the downloader wait out its retries), the average spans four times the longest pause of the last minute, up to 60 seconds, so the speed and the time left stay readable between the bursts. The time left follows from that speed and the size the downloader estimates. Both update every second while the downloader prints nothing, and the speed reads 0 once no byte has arrived for a minute.
- **Size and post-processing of a media download:** the downloaded size of a job that runs through yt-dlp adds up its streams (a video, then its audio) and does not fall back when the next stream starts. While yt-dlp merges or converts the finished streams with FFmpeg, the job reads "Processing with FFmpeg"; that step prints nothing for as long as the local work takes, so a silent post-processor is given one hour where a silent transfer is given three minutes before the download reconnects. A queue's byte quota counts the bytes each run of the downloader receives once, not the size of the merged or converted file. When the downloader starts again (a changed speed limit, a stalled transfer, a lost fragment, a restart of the app), the bytes it resumes from are counted again, and a playlist run that starts again counts its finished items by the size of their files.
- **Live streams** (Twitch, Kick, broadcasters' live HLS and DASH channels and similar) are recorded from the moment the download starts until the stream ends; the list shows the recorded size and speed instead of a percentage. A paused live recording cannot continue the same file.
- **From the stream's beginning:** for a live stream the picker offers **Download from the stream's beginning**. Where the site keeps the running stream from its start (yt-dlp supports this on YouTube and Twitch, for example), the recording begins there and continues while the stream runs; elsewhere (Kick, for example) the stream is recorded from now on and the status says so.
- **Finish live recording and keep it** (Downloads menu, or the right-click menu of a recording row) stops a running live video recording and publishes what was recorded so far as a normal file, without its last second (the frame being written when it stopped).
- **On sites with feeds or previews,** open the video's own page first. DRM-protected streams are not supported.
- **Batch:** a numeric or letter range such as `https://host/img[001-120].jpg` expands into up to 1000 jobs; **File → Batch download** shows an example, **Import list** loads a plain-text URL list and **Export list** writes the selected addresses.
- **Duplicates:** adding an address already in the queue asks once per batch: use the existing job, download a new copy, or cancel.
- **Session cookies:** some downloads need the site's session. Grant **Allow session cookies for this site** in the extension for that one site; nothing is read without that gesture, and **Remove site session permission** withdraws it. The permission covers the downloads from that site, taken-over browser downloads included, until you remove it. The extension's takeover of a browser download sends cookies only when the page the download came from (its referrer) is a site you allowed; a download without a referrer, such as a typed or bookmarked address, is handed over without cookies. Then the cookies that apply to the download address, and to the address it was redirected from when that has the same origin, are read from the browser's regular (non-incognito) cookie store, partitioned cookies are left out because a top-level download has no embedding page, and a download whose cookie store or cookies cannot be verified (no regular tab open, several regular stores, consent recorded for another store) stays in the browser. A download started from an allowed site's frame embedded in another page counts as that site, because its referrer is the frame's address. A download from a site you did not allow is handed over without cookies; if the site needs the session, the app then reports `SSD-NET-004` (see **Sign-in pages**) and hands the download back to the browser (see **Files**); with an app or an extension older than that, the browser's copy is already removed, so allow the site first.
- **Sign-in pages:** a file download whose request was redirected to a web page (`text/html` or `application/xhtml+xml`) that the server does not send as an attachment fails at once with `SSD-NET-004`, without a retry, and nothing is saved: such a page is where a site sends a request that lacks the session, not the file. Download the file in the browser, or allow session cookies for the site from the extension's context menu and add the link again from the browser (right-click it → **Download link with SSDownload**); the extension attaches cookies only to a request it sends itself, so a retry of the failed job and a link added in the app go without them. A taken-over browser download that ends this way is continued by the browser. A page that the request reaches without a redirect, a file whose name ends in `.htm`, `.html` or `.xhtml`, and a page sent as an attachment are saved. An automatic job (**Auto**) whose address leads to a web page is handed to the media tools instead. The experimental browser transfer applies the same rule in the browser: it pauses the job with a message instead of writing a page that a redirect led a file job to, and it never writes a web page for a video or audio job.
- **Expired links:** many addresses redirect to a signed, time-limited address. When the address that a download was redirected to answers 401, 403 or 410, the download asks the original address and follows its redirects to a fresh address, once for each expired address: connections refused together share that one request, and a download over one connection asks at most once. Ranges that are running finish on their open connection and the ranges that start afterwards use the fresh address, but only if it proves the same file: an equal strong ETag, or the same Last-Modified and size, checked with `If-Range` like every resumed range. A fresh address that cannot be reached, answers 401, 403 or 410 again, is another file or is a web page leaves the download with the original refusal and keeps what was downloaded. Asking again is not an attempt and does not use up the retry limit; an address obtained this way is renewed again only after a byte came from it. A refusal from the original address itself (no redirect) is not followed. When the address cannot be renewed, a job that has a page to refresh from waits as **Awaiting source** and any other job fails; **Refresh source address** (or the extension's browser transfer entry) resumes the same job with a fresh address. **Pause all** and **Start now** leave such a job waiting; **Pause all** also cancels a refresh still running for it.
- **Order and priority:** drag rows or use Alt+Home / Alt+End (in the Modern theme, rows can be dragged only while no column is sorted); within a queue, queued work starts in list order, and several queues take turns. **Start now** starts a job immediately, outside the concurrency limit and outside the metered and Battery saver holds below; the free-space check still applies to it.
- **Download window:** one download you start that begins at once opens its own window: **New download** with a single link, a link or a download the browser extension hands over, and **Download** in the picker, which turns into it. Several links added together, a start scheduled for later, the site crawler, synchronization, a queue that starts a job later, **Resume all**, **Retry failed**, automatic retries, jobs restored when the app starts and `ssdownload-cli --add` open none. A download has one window; opening it again brings that window forward. Closing the window never cancels the download.
- **Mini panel and completion card:** **Downloads → Mini panel** (or the tray) opens a small list of active downloads that can be pinned on top. A finished download shows a card with **Open** and **Show in folder**.
- **Tray:** progress on the icon; the menu has the mini panel, new download, add from clipboard, pause/resume all, speed-limit presets, shut down when done, a one-hour quiet mode, the download folder, updates, Settings and Exit.
- **Disk space and sleep:** a job that is about to start is paused with a message when its disk has less than 256 MiB (or less than the remaining size) free; resume it after freeing space. Windows is kept awake while downloads run (the display may still sleep).
- **Metered connection and Battery saver:** two guards in **Settings → Behaviour**, both off by default, hold the whole queue. **Hold downloads on a metered connection** applies while Windows reports the connection as metered (a fixed or variable cost, roaming or a used-up data allowance). **Hold downloads while Windows Battery saver is on** applies while Windows has Battery saver on (Energy saver in recent Windows 11 versions); it starts at the charge level set in Windows, so the app has no threshold of its own. While a guard holds, nothing starts, and running downloads (files, FTP, video and audio) go back to the queue; the status line names the reason, and so does the Phase line of a waiting download's status view; everywhere else a waiting download says only Queued. Once the condition ends, the queue runs again within 15 seconds and only the downloads the hold stopped start again: a download you paused stays paused, and being held does not count as a failed attempt. A running live recording is not stopped by a hold, because a stopped recording cannot continue the same file (see Live streams): it goes on until the stream ends or you pause it, while a live job that has not started yet waits like every other job. A job counts as a live recording once the media analysis has found a live stream. **Start now** still starts a job during a hold, and the hold does not stop it. Windows is asked when the app starts, before any download starts, then every 15 seconds and when a guard is switched. Update checks, media-tool refreshes, synchronization checks and experimental browser transfers are not downloads of the queue and are not held.
- **Basic and Advanced** (`Basit` / `Gelişmiş`) are chosen in the first-run wizard and in Settings (**Interface level**). Advanced adds named queues with time windows and byte quotas, folder rules, a site crawler, periodic synchronization, site logins, the event and job logs and completion actions (notify, shut down, run a program). An action runs once every job of its queue has completed; a failure in the queue or removing one of its jobs cancels the action until new work is added there. Shutting down and running a program also wait until every job in the list has completed (a failed, paused or cancelled job in another queue holds them back until it is retried or removed), and only one countdown runs at a time; cancelling it also cancels the other shutdown and program actions waiting behind it.

## Themes

The first-run wizard and **Settings → General → Theme** choose **Classic** (the default) or **Modern**. The wizard opens before the main window, so its choice applies at once; a choice made once the windows are open (in Settings or in the wizard reopened from it) applies when SSDownload restarts. In both themes the wizard shows each choice as a one-row card: its icon, then its title over its explanation, which wraps to a further line where it is longer than one and is never shortened; Tab goes through the cards row by row and then the buttons. Both themes have the same commands, menus, shortcuts, dialogs and settings, and every command acts on the same jobs. Classic keeps the plain Windows controls. Modern draws the windows in the Windows 11 style and adds:

- Icons on the command buttons (in a narrow window only the icons, with a tooltip that names the shortcut) and access keys on them (Alt plus the underlined letter).
- A pause button whose label follows the selection: **Pause**, **Resume**, or **Pause / Resume** when the selection holds both kinds, which, like Space, pauses the running jobs and resumes the paused ones.
- Esc in the search box clears it (Ctrl+F reaches the search box in both themes).
- Under the list, the **Details**, **Job log** and **Error details** tabs show the selected download's details, its own log (the newest 400 lines) and the error it recorded. **Job log** is there on the Advanced level only, like the job log command. Drag the space between the list and the tabs to give either more room.
- Click a column header to sort the list by that column: once ascending, again descending, a third time back to the queue order. Sizes, speeds and remaining times sort by their values, states in the order a download goes through them. The list sorts again when you click a header, change the filter or the search, show or hide a column, press F5, or the set of listed downloads changes (a download is added or removed, or enters or leaves the filter or the search); in between, rows keep their places while their values change, and the selection and focus stay on the same downloads. Sorting changes only what the list shows, never the queue order or priority: Alt+Home / Alt+End and **Move to top / bottom** still move the jobs in the queue. Right-click the header, or use **View → Columns**, to hide or show columns; **Name** and **State** always stay. **View → Sort by** sorts from the keyboard, and **View → Larger / Smaller details pane** moves the split. The last column fills the width the others leave, and a long location is shortened in the middle. The hidden columns, the sort and the height of the tabs are remembered.
- A failed download shows an error mark before its name and a paused one a pause mark. The progress column shows a thin bar under the percentage: in the Windows accent colour while a job runs, grey while it waits, yellow while it is paused, green when it completed and red when it failed or was cancelled (those two fill the whole bar).
- The row menu groups its commands, with icons and the shortcut of each command.
- **New download** shows a hint in each empty field, and its main button names what it does: **Continue** when a single link opens the format picker, **Download** otherwise (Classic's button says **Continue / Download** for both).
- **New download**, **Settings**, the speed limit, **Rename**, **Queue manager**, **Folder rules**, **Site explorer**, **Sync manager**, **Site logins**, **Event log**, **Job log**, the video picker, the download status view it turns into and the first-run wizard have the same fields and buttons and check them the same way. ## Settings

| Tab | Controls |
|---|---|
| **General** | Interface level (Basic or Advanced) and interface language (Türkçe, English, العربية, Español, Português, Français or Deutsch; the browser extension follows it, and switching to or from Arabic mirrors the windows the next time the app starts); download folder; usage profiles; clipboard detection; start with Windows; minimize to tray; completion notification; dark title bar and controls; theme (Classic or Modern, applies when SSDownload restarts); site entries in the browser; daily working hours; update check; extension install. |
| **Advanced** | Concurrent jobs (1–16, 3 by default); connections per file (1–16, 8 by default); media fragment concurrency (1–16, 4 by default); per-host jobs and connections (1–16, 8 by default); global speed limit (KiB/s, 0 = unlimited); retries in a row without progress (0–20; 0 = no automatic retries); experimental browser transfer; event log level and host recording. |
| **Network** | Proxy: the Windows setting, none, or manual `http://` / `socks5://` with an optional user name and password; a scheduled speed limit (daily window and KiB/s). |
| **Behaviour** | Keep Windows awake while downloading; completion sound; completion card; browser download takeover; hold on a metered connection; hold while Battery saver is on; the Ctrl+Shift+D hotkey; double-click action; history retention in days (0 keeps everything). |

The Basic level shows only **General**; the other tabs keep their saved values.

- **Connections per host:** the per-host limit applies to all downloads from one host together, both to how many of them run at once and to how many connections they hold open. With the default of 8, one file from a host uses up to 8 connections, and two files from the same host share those 8: a connection that cannot open because the host is at its limit waits until another one closes, and a download that waits still counts as a running download. Media downloads keep one connection of the limit free, so they fetch as many fragments at once as the media fragment concurrency allows, up to the limit minus one (4 with the defaults). A profile saved with 4 connections per file, or with a per-host limit of 2, gets 8 for that field the first time the app opens it; every other saved value stays, and so does a value saved later, unless an older version opens and saves the profile: it drops the record of the move, and 4 or 2 then move again.
- **Speed limit:** **Downloads → Speed limit** sets KiB/s for the selected jobs (0 follows the global limit); the tray presets set the global limit. A running live recording keeps the limit it started with, because changing it would restart the capture.
- **Proxy:** the Windows setting is read at start and when the proxy setting is changed in Settings, and only its HTTP/HTTPS entry is used (no automatic configuration script and no SOCKS-only entry). FTP downloads go through a SOCKS5 proxy only; with an HTTP proxy they connect directly. An HTTP proxy password is sent with Basic authentication. If the proxy cannot be used at start (for example its saved password cannot be read), the app shows a warning and connects directly.
- **Site logins** (Advanced): host → user name and password, sent as HTTP Basic credentials only to that exact host over HTTPS (or HTTP when the entry allows it). Letter case, an international spelling and a trailing dot do not make a different host, and a host has one login. A redirect to another host never carries them.
- **Scheduling** uses local time; the start is inclusive, the end exclusive, `23:00–07:00` crosses midnight and equal endpoints mean all day. Manually paused work never resumes by itself.
- **Profiles:** data lives in `%LOCALAPPDATA%\SSDownload`; `--data-dir <folder>` or the `SSDOWNLOAD_HOME` environment variable selects another profile. The most recently registered copy owns the browser connection.
- **Developer mode:** `--debug` or `SSDOWNLOAD_DEBUG=1` adds **Media tools** and **Diagnostics** and shows raw component output; `SSDOWNLOAD_DEBUG=0` turns it off again.

## Recovery

100% transfer progress is not completion: merging and final validation still run, and only **Completed** unlocks **Open file**. Failed jobs keep their data, except a partial file whose SHA-256 (supplied, or published by the source) did not match.

| Symptom | What to do |
|---|---|
| The browser cannot connect | When the app or the extension is older than the other, the message says which one to update: the app through **Help → Check for updates**, the extension by the browser's own update or at once on its extensions page (Developer mode, **Update**). Otherwise register the copy you use. |
| A second launch while SSDownload runs | The running copy comes to the front; no second instance starts. If that copy is still closing, the new one starts as soon as it has exited. |
| Download stays disabled after analysis | Read the error, fix the source or session, analyze again. |
| A quality or track disappeared | Analyze again and choose an available option; nothing is substituted silently. |
| Signed address expired | The download asks the original address again and goes on with the fresh address it redirects to. When that is not possible, a job that has a page to refresh from waits for **Refresh source address** instead of failing; any other job fails. |
| `SSD-NET-004`: the source answered with a sign-in or web page | The file needs your session. Download it in the browser, or allow session cookies for the site from the extension's context menu and add the link again from the browser (**Download link with SSDownload**). |
| Merge fails or a work folder remains | Free space and resume; parts stay under `<destination>\.ssdownload-work\jobs\<job-id>`. |
| `SSD-TOL-005`: the media tools' path is too long | Windows starts a program only from a path of at most 259 characters, and yt-dlp starts FFmpeg, FFprobe and Deno itself from paths that begin with `\\?\` (the prefix counts): from a longer path it carries on without them and can leave streams unmerged or in the wrong container, so the analysis and every download that runs yt-dlp are refused up front. The app's own HLS downloader does not run yt-dlp and is not refused. The tools sit about 120 characters below the profile folder (`<profile>\tools\versions\<id>\…`). Move the profile folder to a shorter path and start SSDownload with `--data-dir <that folder>` or `SSDOWNLOAD_HOME`; a `--data-dir` that names another folder opens a separate, empty profile. A long download folder is not affected: the media workspace in it is opened with the extended-length prefix. |
| Media verification: the file's content does not match its extension | The file holds another container than its name says (for example MPEG-TS under `.mp4`), so it is not published. Download it again; if it repeats, the source delivers that container every time: pick another container in the picker, or report the log. A single file relayed by the experimental browser transfer is copied into the job's container before it is checked. |
| Remove hits a sharing violation | Close the program holding the file and retry. |
| The queue cannot be saved | Active jobs pause and new work waits while saving is retried. |
| Encrypted records do not open | Records are bound to the Windows user (DPAPI). Unreadable ones move to quarantine and return when the profile is opened under the original account again. |
| Database from a newer version | An older build refuses a newer database instead of rewriting it. |

## Error codes and logs

- Classified failures carry permanent `SSD-<area>-<number>` codes with a message in every interface language. Areas: `BRG` browser bridge, `MED` media resolution, `NET` network, `TRF` transfer, `STO` storage, `RCV` recovery, `TOL` media tools, `UPD` updates, `EXT` extension. Codes are never renumbered or reused.
- Logs live in `<profile>\logs\`: `events-YYYYMMDD.jsonl` and `ssdownload-YYYYMMDD.log`, rotating at 5 MB with five kept and removed after 30 days, plus per-job timelines in `logs\jobs\`. The browser connection appends its refusals to the same files (channel `native-host`) and leaves rotation to the app; it writes nothing when it cannot read the profile settings. URLs are logged without credentials, query or fragment; with **Log site names** off, site names are hidden as well, also in error messages that repeat the download's site or name a host after `host:`, `host=` or `connect to`.
- **Report problem** (on a failed analysis or job) and **Tools → Diagnostics** write a local folder and ZIP. Nothing is uploaded; look through it before sharing it in an issue. A **Report problem** folder can include the failing page's markup as `sayfa.html`, unredacted: the copy the browser handed over or, without one, the page read once by the app (address without query or fragment, no cookies, credentials or referer).

## Data and uninstall

- Uninstalling removes the program, its shortcuts and browser registration, and **keeps your downloads and your profile**.
- Deleting `%LOCALAPPDATA%\SSDownload` removes the queue, settings, logs and media tools. A `.ssdownload-work` folder in a download folder holds unfinished jobs.
